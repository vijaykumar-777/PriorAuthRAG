# Phase 5.3 Context: Production-Like Testing Runner Harness & Batch Execution Pipeline

**Phase:** 5.3 (Part 3 of 3-Week Technical Task Checklist)  
**Status:** Discussed & Decisions Locked  
**Created:** 2026-09-30

## 1. Executive Objective
Build and execute a robust, production-like testing runner harness (`scripts/run_pa_test_harness.py`) that feeds the 50 synthetic patient cases into the Prior Authorization pipeline, capturing end-to-end system determinations, criterion-by-criterion evaluations, supporting patient evidence, policy citations, and missing documentation without ever exposing the system to the ground truth answer keys.

---

## 2. Locked Decisions

### Decision 1: Execution & Checkpoint Architecture
- **Sequential Execution with Live Checkpointing:**
  - Cases `SYN-001` through `SYN-050` are processed sequentially.
  - Per-case results are written immediately to `data/test_runs/latest/cases/<Case_ID>.json`.
  - Resumable: If interrupted or if rate limits hit, re-running the harness automatically skips already completed cases unless `--force` is specified.
  - Master run ledger saved to `data/test_runs/latest/system_run_results.json`.

### Decision 2: 2-Stage Blind Clinical Determination Flow
The system must be evaluated strictly under real-world clinical conditions without seeing the ground-truth answer keys (`Policy_Ground_Truth.xlsx` is strictly walled off):
1. **Stage A — Policy Retrieval via RAG Pipeline:**
   - Input to RAG: Payer (`Cigna`), CPT code, Procedure description, Clinical condition.
   - Executes hierarchical pipeline: Stage 1 Master Table check -> Stage 2 TOC Section Router -> Stage 3 Scoped Hybrid Retrieval.
   - Extracts relevant policy rules, thresholds, exclusions, and documentation requirements directly from `Cigna_ACDF.pdf`.
2. **Stage B — Clinical Evidence Determination Engine:**
   - Input: Retrieved policy rules from Stage A + Patient's actual submitted EHR documents (`physician_note.txt`, `mri_report.txt`, `xray_report.txt`, `pt_notes.txt`, `lab_report.txt`).
   - Evaluates each policy criterion independently:
     - `Status`: `MET`, `NOT MET`, `UNKNOWN`, `CONFLICT`
     - `Patient Evidence`: Verbatim quote or specific finding from the patient record
     - `Policy Evidence`: Specific requirement and section from the retrieved policy
     - `Missing Information`: Identification of omitted mandatory reports/tests
   - Computes system overall determination (`MET`, `NOT MET`, `UNKNOWN`, `CONFLICT`).

### Decision 3: Rate Limiting & Resilience
- Built-in adaptive throttle: 1.5-second pacing delay between LLM calls.
- Exponential backoff retry handler: Automatically catches HTTP 429 / Rate Limit errors from Groq API, backing off (2s, 4s, 8s, 16s) before retrying.
- Deterministic fallback parser: If LLM output fails JSON parsing, triggers multi-tier regex/repair to ensure zero pipeline crashes.

### Decision 4: Output Data Contract
For every case processed, the harness must capture:
- `case_id`
- `cpt`
- `condition`
- `payer`
- `pa_required` (`Yes` / `Add On` / `No`)
- `selected_policy` (`CMM-601: Anterior Cervical Discectomy and Fusion`)
- `retrieved_sections` (e.g. `['S9.1.1', 'S9.1.2']`)
- `system_overall_result` (`MET` / `NOT MET` / `UNKNOWN` / `CONFLICT`)
- `criterion_evaluations`: list of:
  - `criterion_id`
  - `criterion_description`
  - `system_result` (`MET` / `NOT MET` / `UNKNOWN` / `CONFLICT`)
  - `patient_evidence`
  - `policy_citation`
- `missing_information` (list of missing records)
- `runtime_seconds`
